### Visual exploration with Painter

- Use `painter` for open-ended visual design, substantial layout exploration, or a request for a different visual direction, without waiting for the user to name the tool. For precise edits to an established design, work directly in code unless exploration is requested. Review-only work does not require generating alternatives.
- Ground the prompt in the primary task, required content and states, product constraints, and existing visual language. Supply an available screenshot for an existing UI, using synthetic or non-sensitive data. Explore two or three genuinely different arrangements unless the user has chosen a direction; a single labelled comparison image is often enough.
- Inspect concepts for hierarchy, realistic content, accessibility risks, and invented behavior. Recommend the strongest direction with a brief reason, not a gallery the user must manage. Refine a selected concept rather than restarting. When implementation is already requested, continue without adding an approval gate; for exploration-only requests, let the user choose before implementing.
- Treat generated concepts as design references, not working UI or verification evidence. Preserve real components and behavior when implementing, then render, critique, fix, and inspect the actual interface. If Painter is unavailable, compare arrangements with a lightweight sketch or code prototype and continue; disclose any remaining verification gap.
